## 补偿方案

针对本次清退，**SparkVM** 提供以下两种处理方案，用户可根据自身需求选择其一。

### 方案一：更换为对应同规格 CloudX-NP 系列产品

可更换为对应的 CloudX-NP 系列 SKU。为感谢所有用户的一路陪伴，选择此方案的用户将统一享受 **7 折优惠**。

#### 更换原则

1. **仅支持同规格替换**。
2. 选择更换产品方案的用户，**无需重装系统**。
3. 原服务中的 **eth0 IP 地址不会发生变化**。
4. 原 **DGM-CT 线路对应网卡将被移除**，相关网络能力将不再保留。
5. 由于 **CloudX-NP 系列产品价格低于 CloudX-CT 系列产品**，**SparkVM** 将通过**延长服务时长**的方式进行差额补偿。
6. 选择此方案后，将统一应用 **7 折循环折扣**。若原服务已生效的循环折扣高于 7 折（即折扣力度更小），则将统一更换为 7 折；若原服务已享有 7 折或更低折扣，则**保留原有折扣不变**。

#### 延长时长计算原则

按原服务剩余未使用价值，折算为目标 CloudX-NP 同规格产品的可用时长。可按以下公式理解：

$$
\text{新服务可用时长} = \frac{\text{原服务剩余未使用金额}}{\text{对应 CloudX NP 同规格产品当前日均价格}}
$$

如原服务存在循环折扣，则其日均价格按折后价格计算，即：

$$
\text{当前日均价格} = \frac{\text{CloudX NP 同规格产品当前计费周期价格} \times \text{循环折扣系数}}{\text{当前计费周期天数}}
$$

### 方案二：按未使用时长等比例退款

如不选择更换产品，**SparkVM** 将按服务**剩余未使用时间等比例退款**，并通过**原支付渠道原路退回**。

提交退款申请后，**财务预计将在 3 个工作日内完成处理**。

## 写在最后

本次线路关停后，我们短期内将不再面向个人用户提供含公网入口的 VM 服务。借此机会，想和大家聊聊 SparkVM 这一路走来的故事。

SparkVM 是我们面向 C 端用户的第一次探索与尝试。

它缘起于 "IEPL VM for BGP Players"——最早的交付甚至是手搓脚本完成的。在这个过程中，我们逐步搭建并完善了 VM 基础设施、管理控制台和自动化交付流程，一点一点把它做成了一个真正的产品。

最初的目标很纯粹：探索 IX Peering 的更多玩法。所以一开始上线的只有 CloudX-NP，因为我们深知自身在 ToC 场景下应对国内公网合规的经验不足，不敢贸然涉足。

后来，许多朋友希望添加公网入口。我们审慎评估后，决定仅开放 IPv6 接入，试图在满足需求的同时继续把控风险。但事实证明，我们在这方面的经验确实欠缺。

我们期待和大家一起成长，但环境并没有给我们这样的机会。当前的监管态势下，一旦收到通报即面临拔线，没有缓冲余地。

自 2026 年 4 月以来，随着监管力度加大，SparkVM 开始收到通报。截至目前，由 SparkVM 引发的通报共计 **2 起**，均为 C 端客户使用未备案域名运行 TLS / HTTP 协议所致。

经过审慎评估，我们认识到：**国内公网入口 + C 端客户** 这一组合所叠加的不可控风险，加上我们在 ToC 风险管控方面经验的不足，是业务不稳定的根本来源。为此我们折腾了许多次，大家也跟着折腾了好几次，对此深表歉意。

因此，我们做出了一个艰难但必要的决定——**短期内不再面向个人用户提供含公网入口的 IaaS 服务**。

兜兜转转，又回到了最初只有 CloudX-NP 的样子。

**但请放心，IX Peering VM 我们将继续提供服务。** 从上线至今的服务稳定性，相信大家有目共睹。

后续，我们将回归 **SD-WAN / 专线业务**的主线，同时继续探索 IX Peering 的更多玩法，以及**网络能力的 SaaS 化**。
